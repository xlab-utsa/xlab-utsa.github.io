# X-Lab Schema Visualizer

Two views into the site's content data schema (`../../types/content.ts`, documented in `../../docs/SCHEMA.md`), switchable via tabs at the top:

1. **Schema Diagram** — interactive, drag/zoom/pan ER diagram. Built with React Flow — dark card-per-entity style, field-level connector lines for foreign keys, click a card for a full detail panel (fields, rationale, relationships, live record counts from the real `content/` directory).
2. **Data Explorer** — browse a large synthetic dataset shaped to the schema (231 fake records across all 11 entities), with resolved relationships (click a foreign key, jump to what it points at) and a coverage dashboard showing exactly which enum values / field-presence patterns / relationship shapes are represented and how many times.

**This app is not part of the deployed site.** It never gets built, bundled, or deployed with `xlab-utsa.github.io` — it's a standalone dev tool that lives in `labbench/` specifically so it can't accidentally end up in the production build. See `labbench/README.md`.

## Run it

```bash
npm install
npm run dev
```

Opens on the usual Vite dev port. `npm run build` produces a static `dist/` you can open locally or drag into a static file server — still never deployed anywhere.

## How it stays accurate

- **Schema**: hand-encoded in `src/lib/schema-graph.ts`, mirroring `../../types/content.ts` and `../../docs/SCHEMA.md`. If the real schema changes, update this file to match — there's no automated sync (the real schema is TypeScript interfaces for a Next.js app that doesn't exist yet; this file is a deliberate, readable re-encoding of it for visualization, not a parser).
- **Record counts**: live. `scripts/scan-content.mjs` scans the real `../../content/` directory and writes `src/content-status.generated.json` — this runs automatically before both `dev` and `build` (via npm's `predev`/`prebuild` hooks), so the counts shown on each card always reflect the actual current state of `content/`, not a stale snapshot. Run `npm run scan` to refresh it manually.
- **Layout**: computed, not hand-placed. `src/lib/layout.ts` runs `@dagrejs/dagre` against the real field-derived card dimensions (`estimateNodeHeight` in `schema-graph.ts` mirrors `EntityCard`'s actual row math) and the FK edge graph, producing a hierarchical left-to-right arrangement with guaranteed no overlaps. Run `npm run verify-layout` after adding/removing entities or fields — it's a standalone numeric check (no browser needed) that prints every card's computed box and flags any overlap, so a layout regression is caught before you even open the app.

## Dragging and layout

Nodes are draggable (React Flow's `useNodesState`/`onNodesChange` wiring — dragging updates real component state, so it persists through search/filtering). The initial hierarchical layout is a starting point, not a cage: rearrange anything, it stays put. There's no "reset layout" button by design — reload the page to get back to the computed layout.

## What you get — Schema Diagram

- Every entity as a table-style card: header (name + tier badge + live record count), field rows (name, type, required/optional marker, PK/FK icon).
- Dashed connector lines from FK fields to the specific `id` row they reference (not just card-to-card).
- Click a card → detail panel: full field list with notes, the design rationale for that entity, and its incoming/outgoing relationships.
- Search box: filters/highlights entities and fields by name or type.
- Toggle: show/hide SECONDARY-tier entities (Recognition, ServiceRecord, Course, Sponsor) to focus on the CORE schema.
- Drag any card to rearrange; pan/zoom/minimap for navigating the whole graph.

## What you get — Data Explorer

- Left sidebar: all 11 entities with live record counts, click to browse.
- Middle: a searchable/filterable record list — filter by any "coverage tag" (e.g. `personType=postdoc`, `multi-institution-3`, `no-body`) to jump straight to records demonstrating a specific case.
- Right: full record detail — every field's raw value, plus resolved relationships in both directions (outgoing FKs *and* who points at this record) as clickable jumps, so you can walk the graph record-by-record instead of just structurally.
- "Coverage dashboard" button (top right): every entity's tags and counts at a glance — the answer to "did we actually cover X?" without hunting through records.

## The synthetic dataset

`src/synthetic/data.generated.json` (231 records) is generated by `scripts/generate-synthetic-data.mjs` — **not** random noise and **not** a full combinatorial explosion (Person alone has enough independent axes — 7 personTypes × 5 affiliation patterns × 3 profile-richness tiers × 4 tenure states — that a true cartesian product would be 1000+ near-duplicate records with no diagnostic value). Instead, deliberately:

1. Every enum value is represented (all 7 `personType`s, all 6 `Publication.category`s, all 5 `Recognition.category`s, etc.).
2. Every meaningful relationship pattern is represented: zero affiliations, one, many across multiple institutions, overlapping affiliation history at the same institution (mirrors the real PI's UB→UTSA transition), orphan records with no FK set, fan-in (multiple records pointing at the same target).
3. Every optional-field "richness tier" is represented (minimal record with only required fields / typical / maximal with every optional field populated) — instead of every individual field-presence permutation.

Every record carries a `_covers` tag list saying exactly which case it demonstrates, which is what the Data Explorer's tag filter and coverage dashboard are built on.

**Regenerate** after changing the schema or the coverage cases: `npm run generate-data` (deterministic — seeded, so output is stable/diffable across runs unless the generator logic itself changes). This is a manual step, unlike `scan-content` — the synthetic dataset doesn't reflect real `content/` state, so there's no reason to regenerate it automatically on every `dev`/`build`.

All names/institutions/text in it are fake (`@faker-js/faker`, seeded) — never real people or real lab data.
